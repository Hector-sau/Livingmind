# LivingMind 主流项目指标与面试证据指南

更新：2026-09-18

这份文档只保留技术面试中常见、容易解释且真正有价值的数字。项目不需要给每个模块都制造百分比；大多数能力用“实现了什么、怎样保证正确、有哪些测试”说明即可。

> 口径纪律：模拟场景可以作为测试数据，但结果必须由实际运行得到。没有运行过的数字只能标为“待测”或“目标”。

## 1. 最值得准备的四类数字

| 优先级 | 数字维度 | 面试官想了解什么 | LivingMind 如何测 |
|---|---|---|---|
| 1 | AI 与接口响应效率 | 用户要等多久，优化有没有真实作用 | 模型调用与端到端计划的 P50、P95、最大延迟；优化前后延迟变化 |
| 2 | Redis 缓存效果 | 为什么引入缓存，是否减少数据库压力 | 命中率、命中/未命中 P95、吞吐量、数据库查询次数变化 |
| 3 | 稳定性与工程规模 | 系统是否可靠，异常路径是否考虑过 | 自动化测试数量、端到端场景数、重复执行数、停止后新增动作数 |
| 4 | 能源效果 | 产品是否产生可解释的业务效果 | 购电量、峰值购电、日成本和舒适约束 |

简历通常保留其中两到四组数字就够了，不需要把 Memory、Harness、LangGraph、PostgreSQL、Kafka 分别写一个准确率。

## 3. 响应效率：最重要的性能指标

### 3.1 应该记录什么

| 指标 | 定义 | 用途 |
|---|---|---|
| 模型 P50 | 50%的模型调用不超过该时间 | 表示日常体验 |
| 模型 P95 | 95%的模型调用不超过该时间 | 表示慢请求体验，面试中比平均值更有价值 |
| 端到端计划 P95 | App/API提交请求到计划返回的95分位耗时 | 包含路由、Memory、Agent、校验与序列化 |
| 规则快速路径 P95 | 明确设备指令或规则计划的95分位耗时 | 证明不是所有请求都调用大模型 |
| 超时/降级次数 | 模型超时或非法输出后使用规则的次数 | 说明系统在外部模型不稳定时仍可用 |
| 单请求成本 | 输入/输出Token及模型费用 | 有稳定调用量后再统计，当前代码尚未记录 |

延迟优化公式：

```text
延迟下降率 = (优化前 P95 - 优化后 P95) / 优化前 P95 × 100%
```

不能把8秒目标与2035 ms单次调用计算成“提速74.6%”，因为8秒是预算，不是优化前基线。

### 3.2 DeepSeek 基线怎么建立

使用现有15条设计用例运行3轮，共45次真实调用。固定模型、温度、超时、提示词和用例版本，记录：

- 模型调用 P50、P95和最大延迟。
- 端到端计划 P50、P95。
- 成功、超时、非法输出和规则降级次数。
- 模型名称、提交哈希、日期和网络环境。

现有入口：

```bash
cd backend
set -a && source .env && set +a
.venv/bin/python scripts/e2e_real_model.py --eval
```

截至本文更新，这45次调用**尚未执行**，当前仍只有2035 ms单次样本。

### 3.3 值得做的前后对比

只选择能解释响应效率的改动：

1. 缩短重复提示词，比较模型P50/P95。
2. 对“关灯、停止、查询状态”等明确命令使用规则快速路径，比较端到端P95和模型调用次数。
3. 对格式错误只进行一次有限修复，比较成功次数提升与P95代价。
4. 保留Pydantic、偏离上限与Harness校验；不能为了速度删除安全边界。

## 4. Redis：最适合做性能前后对比的基础设施

Redis在LivingMind中的目标用途是缓存热点人物偏好、设备快照和短期幂等结果，同时承担有TTL的冷却和短锁。它不是业务事实来源。

### 4.1 面试常见指标

| 指标 | 定义 | 为什么重要 |
|---|---|---|
| Cache Hit Rate | 命中缓存的读取数 / 总读取数 | 判断缓存是否真的覆盖热点请求 |
| Cache Miss Rate | 未命中数 / 总读取数 | 解释数据库回源压力 |
| P50/P95 Latency | 缓存命中、未命中和无缓存三种路径分别统计 | 证明Redis改善了尾延迟 |
| Throughput / RPS | 每秒完成的请求数 | 观察缓存是否提高接口处理能力 |
| DB Query Reduction | 引入缓存前后数据库查询次数变化 | 证明Redis减少了数据库负载 |
| Fallback Success | Redis断开时请求是否回退PostgreSQL并返回正确结果 | 证明缓存故障不会让核心服务失效 |

核心公式：

```text
缓存命中率 = cache_hits / (cache_hits + cache_misses)

数据库查询下降率 = (无缓存查询数 - 有缓存查询数) / 无缓存查询数 × 100%

吞吐提升率 = (缓存后 RPS - 缓存前 RPS) / 缓存前 RPS × 100%
```

### 4.2 公平的测试方式

T4实现后，用同一数据、同一机器和同一并发度分别运行：

1. PostgreSQL直读，不启用Redis。
2. Redis冷缓存，包含首次回源。
3. Redis热缓存，缓存已预热。
4. Redis被停止，验证PostgreSQL降级。

建议固定1000次人物偏好/设备快照读取，并分别测试并发1、10、20。记录命中率、P50、P95、RPS和数据库查询次数。具体请求数可以根据机器性能调整，但前后必须保持一致。

结果模板：

| 场景 | 命中率 | P50 | P95 | RPS | DB查询数 |
|---|---:|---:|---:|---:|---:|
| 无Redis | 不适用 | 待测 | 待测 | 待测 | 待测 |
| Redis冷缓存 | 待测 | 待测 | 待测 | 待测 | 待测 |
| Redis热缓存 | 待测 | 待测 | 待测 | 待测 | 待测 |
| Redis断开降级 | 0% | 待测 | 待测 | 待测 | 待测 |

Redis尚未接入，因此这些字段都必须保持“待测”。

## 5. 其他模块怎样表达，不强行做百分比

| 模块 | 面试时重点说什么 | 最合适的证据 |
|---|---|---|
| Main Agent | 如何路由和编排两个专业Agent | 一条真实协作轨迹和分支测试 |
| Memory | `accountId/personId/spaceId`如何隔离人物偏好 | A/B人物切换测试、访客默认值、无跨人物暴露 |
| Harness | 模型为什么不能直接控制设备 | 白名单、参数范围、确认、停止、执行前guard的故障测试 |
| PostgreSQL | 为什么它是业务事实来源 | 重启后数据仍存在、事务失败不留半个服务、并发确认只成功一次 |
| LangGraph | 为什么需要状态图和checkpoint | legacy/graph输出等价、节点轨迹、一次中断恢复演示 |
| Kafka + Outbox | 怎样解决数据库成功但消息丢失 | Kafka停机时设备仍执行，Outbox保留事件，恢复后补发且不重复投影 |
| Docker | 怎样降低环境差异 | 一条启动命令、健康检查、容器内测试通过 |
| Harness/停止语义 | 停止是否真正优先 | 停止后新增动作数为0；这是确定性结果，不必写百分比 |

这些内容的价值来自设计取舍和可复现实验，不来自人为制造“99%”。

## 6. 稳定性数字怎么用

稳定性优先使用规模和确定性结果：

- 115项后端测试、31项前端测试、20项端到端场景。
- 重复确认同一计划只执行一次。
- 同一空间只允许一个运行服务。
- 停止后新增设备动作数为0。
- 设备失败时服务不会误报完成。
- Kafka接入后，故障期间Outbox事件丢失数应为0。

只有做了持续压力测试，才使用错误率、可用性、MTTR等生产指标。当前概念原型不需要写“99.99%可用性”。

## 7. 推荐保留在简历里的数字

### 当前可用

- 通过115项后端测试、31项前端逻辑测试和20项浏览器端到端场景，覆盖计划确认、停止抢占、设备失败、状态回读和整晚服务。
- 接入DeepSeek生成结构化体验计划，并以JSON mode、Pydantic校验、偏离上限和规则降级保证安全；一次真实调用在2035 ms内返回合法结果，当前仅为单次样本。
- 在给定的24小时家庭能源固定日仿真中，MATD3框架结果相较规则策略将模拟购电量降低94.4%、峰值购电降低81.0%，同时保持舒适违规为0。

### 完成测试后再使用

- 通过`[实际优化方法]`将计划生成P95延迟从`[基线]`降低至`[优化后]`，下降`[实际比例]`；45次真实模型调用中发生`[数量]`次规则降级。
- 使用Redis缓存人物偏好与设备快照，在`[并发度]`下实现`[命中率]`缓存命中率，将接口P95从`[基线]`降低至`[优化后]`，数据库查询量减少`[实际比例]`。

方括号必须由真实运行结果替换。通常这两条性能数字加一条能源数字、再加测试规模，就已经足够。

## 8. 面试时回答性能数字的顺序

1. **原问题**：例如模型响应慢、数据库重复读取多。
2. **基线**：同一环境下的P50、P95、RPS或查询数。
3. **技术改动**：提示词缩短、规则快速路径或Redis缓存。
4. **优化后结果**：明确单位和变化比例。
5. **代价**：缓存一致性、额外内存、有限重试带来的尾延迟。
6. **边界**：数据来自设计场景和本地环境，不代表生产流量。

面试官真正关心的是你是否理解为什么指标变化，而不是百分比越多越好。
