# LivingMind 项目指标、技术成效与简历证据指南

更新：2026-09-18

这份文档帮助团队理解三件事：项目通过什么技术解决什么问题、应当用什么指标证明、哪些数字已经可以使用。它也是后续补测、汇报和简历写作的证据入口。

> 口径纪律：模拟场景可以作为测试数据，但结果必须由实际脚本运行得到。没有运行过的数字只能标为“目标”或“待测”，不能写成“已实现”。

## 1. 指标状态怎么读

| 标记 | 含义 | 能否写进简历 |
|---|---|---|
| 已验证 | 有代码、运行结果和证据位置 | 可以，但要保留样本量与场景限定 |
| 单次样本 | 真实运行过，但样本不足以代表稳定表现 | 可以写具体单次结果，不能写稳定率或提升百分比 |
| 已设计 | 测试集、公式或脚本已经存在，但尚未运行真实目标环境 | 只能写“建立了评测方法”，不能写结果百分比 |
| 待实现 | 对应技术尚未接入 | 不能写成项目已使用 |
| 目标 | 团队希望达到的门槛 | 只能用于计划、验收标准或汇报路线图 |

“准确率 96%”必须能回答：总共多少条、什么数据、怎样判定正确、运行了几轮、失败的是什么。

能源指标换算：

```text
购电量下降 = (13.61 - 0.76) / 13.61 = 94.4%
峰值购电下降 = (1.95 - 0.37) / 1.95 = 81.0%
日成本改善 = 1.87 - (-0.02) = 1.89 USD/day
```

日成本跨过了零点，应写“由 $1.87 成本变为 $0.02 净收益”或“改善 $1.89/天”，不建议写超过 100% 的成本下降率。

## 3. 技术、问题、功能与指标的对应关系

| 技术或模块 | 解决的问题 | 项目中的功能 | 推荐指标 | 当前状态 |
|---|---|---|---|---|
| Main Agent / Orchestrator | 用户请求要走哪条处理链路 | 休息、设备指令、状态查询和其他请求的路由与协作轨迹 | 意图路由准确率、错误路由率 | 规则实现；尚无真实百分比 |
| Experience Agent + DeepSeek | 把自然语言转成结构化体验目标 | 生成灯光、温度、窗帘目标；失败自动降级 | 结构化计划一次成功率、评测通过率、降级率、P50/P95 延迟 | 一次真实调用；15条评测方法已设计 |
| Memory | 共享平板上按人物使用独立偏好 | 读取和编辑本人偏好，访客使用空间默认值 | 偏好读取正确率、人物隔离正确率、跨人物泄漏率 | 内存实现；有隔离测试，无汇总百分比 |
| Energy Intelligence | 在舒适条件内考虑用能 | 分时电价规则、舒适优先 / 节能模式、离线能源展示 | 舒适约束满足率、购电量、峰值功率、日成本 | 在线规则 + 固定日离线结果 |
| Space Execution Agent | 把体验目标变成设备动作 | 设备能力匹配、动作规划、整晚步骤 | 动作映射正确率、不支持动作识别率 | 规则实现；有测试，无汇总百分比 |
| Harness + Executor | 防止模型越权和停止后继续动作 | 白名单、参数范围、确认、停止、幂等、每动作前 guard、回读 | 非法动作拦截率、停止后新增动作数、重复执行数、回读一致率 | 已实现于虚拟设备 |
| 服务状态机 | 让一次表达变成持续服务 | 计划、确认、运行、调整、唤醒、停止和失败 | 端到端闭环成功率、状态转换错误率 | 已实现模拟闭环 |
| PostgreSQL | 进程重启后仍保存业务事实 | 目标：人物记忆、计划、服务、动作、活动、Outbox、checkpoint | 重启恢复率、并发确认冲突、重复服务数 | 待实现 T2 |
| LangGraph | 让 Agent 流程可观察、可恢复、可分支 | 目标：1+2 Agent 状态图与 checkpoint | 节点成功率、checkpoint 恢复率、legacy/graph 等价率 | 待实现 T3 |
| Redis | 多实例之间进行短期协调 | 目标：空间锁、冷却、短期幂等和热点缓存 | 并发冲突率、缓存命中率、P95 延迟变化、降级成功率 | 待实现 T4 |
| Kafka + Outbox | 异步传播已发生的事实且不阻塞控制 | 目标：活动投影、审计和分析事件 | 事件补发成功率、丢失率、重复投影率、积压恢复时间 | 待实现 T5 |
| Docker Compose | 降低环境差异和新成员上手成本 | 目标：一键启动后端及基础设施 | 冷启动时间、人工步骤数、环境问题数 | 待实现 T1–T6 |

### 为什么当前不写“检索成功率”

LivingMind 当前没有向量数据库、Embedding 或 RAG 检索链路。人物 Memory 是按 `personId + spaceId` 精确读取结构化偏好，因此更准确的指标是：

- 偏好读取正确率。
- 人物隔离正确率。
- 跨人物数据泄漏率。
- 更新后读取一致率。
- PostgreSQL 接入后的重启恢复率。

只有以后真正加入文档检索或向量记忆，才使用 Recall@K、Precision@K、MRR、命中率等检索指标。

## 4. 核心指标公式

```text
意图路由准确率 = 正确路由请求数 / 总请求数

结构化计划一次成功率 = 首次通过 JSON + Pydantic 校验的模型响应数 / 模型调用数

模型评测通过率 = 满足用例期望方向的计划数 / 非降级评测用例数

规则降级率 = 使用 rule_fallback 的请求数 / 模型模式请求数

人物隔离正确率 = 只使用当前人物偏好的用例数 / 人物隔离用例数

跨人物泄漏率 = 错误暴露或使用其他人物偏好的用例数 / 人物隔离用例数

非法动作拦截率 = 被 Harness 正确拒绝的非法动作数 / 注入的非法动作数

端到端闭环成功率 = 完成计划、确认、执行、事件调整与停止的场景数 / 总闭环场景数

事件补发成功率 = Kafka 恢复后成功发布的 pending Outbox 数 / 停机期间生成的 Outbox 数

延迟下降率 = (优化前延迟 - 优化后延迟) / 优化前延迟

吞吐提升率 = (优化后吞吐 - 优化前吞吐) / 优化前吞吐
```

延迟下降 75% 与吞吐变为 4 倍不是同一种表述，不能混写。

## 5. DeepSeek 多轮评测与优化方案

本节是已批准的后续评测方案，**截至本文更新尚未运行**。

### 5.1 第一阶段：冻结15条用例并建立基线

保持模型、温度、超时、提示词和评测集版本不变，将现有15条用例完整运行3轮，共45次真实调用。记录：

- 通过、方向错误、降级各多少次。
- JSON 解析成功率与 Pydantic 结构校验成功率。
- 模型计划采用率与规则降级率。
- P50、P95、最大延迟。
- 按 baseline、temperature、light、curtain、guest、guard、off-topic 标签统计。
- 模型名称、评测集版本、运行日期与失败原因。

现有入口：

```bash
cd backend
set -a && source .env && set +a
.venv/bin/python scripts/e2e_real_model.py --eval
```

密钥只保存在本机 `backend/.env`。运行输出不得包含或提交 API Key。

### 5.2 第二阶段：扩展到50条设计用例

建议分布：

| 类型 | 数量 | 主要验证内容 |
|---|---:|---|
| 无附加条件的休息请求 | 6 | 是否保持本人偏好 |
| 冷热表达 | 8 | 温度方向和无关设备保持 |
| 灯光表达 | 6 | 明暗方向、上限和“关灯” |
| 窗帘表达 | 6 | 开合方向、隐私和噪声语义 |
| 多条件组合 | 8 | 同时处理两到三个明确要求 |
| 含糊或题外请求 | 6 | 澄清标记与安全默认方案 |
| 越界或对抗请求 | 6 | 偏离上限和 Harness 拦截 |
| 访客与人物隔离 | 4 | 不引用他人偏好、不推测访客习惯 |
| 合计 | 50 | Home Living 模拟评测集 |

为了避免“针对答案调提示词”，建议30条作为开发集，20条作为从未参与调优的保留测试集。简历优先报告保留集结果。

### 5.3 可尝试的优化方法

每次只改变一个变量，并用相同保留集重新测试：

1. **提示词契约更清晰**：明确“只改变用户明确提到的设备，其余保持偏好”，减少无关设置漂移。
2. **加入少量边界示例**：覆盖“有点热”“别太冷”“灯关了”“留条缝”和题外请求，但避免把全部测试答案写进提示词。
3. **降低随机性**：比较当前 temperature 与更低 temperature 对稳定性和重复结果的影响。它主要改善一致性，不应预先宣称提速。
4. **缩短提示词和输出字段**：删除重复说明，在结构不变的前提下比较 P50/P95 延迟与输出质量。
5. **确定性快速路径**：明确的“关灯”“停止”“设备状态”继续走规则或专用分支，减少不必要的模型调用；单独统计跳过模型后的端到端延迟。
6. **有限修复或重试**：只对可恢复的格式错误进行一次修复；比较成功率提升与额外 P95 延迟，避免无限重试。
7. **保持 Harness 后验约束**：无论提示词多好，Pydantic、偏离上限和 Executor guard 都不能删除。

## 6. Memory、Harness 与服务闭环的补测方案

### Memory

- 为3位成员、1位访客设计读取、更新、切换和重置用例。
- 每条计划检查实际使用的 `personId`、温度、灯光和窗帘偏好。
- 任何返回他人私人偏好的行为记为泄漏。
- PostgreSQL 接入后重复同一批测试，并加入进程重启。

建议报告：人物隔离正确率、泄漏率、更新后读取一致率、重启恢复率。

### Harness

注入非法设备、越界温度、越界百分比、过期计划、重复确认、停止后的旧动作、回读异常和部分设备失败。

建议报告：非法动作拦截率、重复执行数、停止后新增动作数、回读异常识别率。

### 服务闭环

每个场景必须走完：

```text
提出需求 → 生成计划 → 用户确认 → 设备写入与回读
→ 模拟入睡 → 环境调整或整晚步骤 → 渐进唤醒或停止
```

建议报告：完整闭环成功率、失败阶段分布、平均完成时间；规则模式与模型模式分开统计。

## 7. 工程化升级后的前后对比

下面是测量计划，不是现有结果。

| 阶段 | 当前基线 | 技术改造 | 改造后必须测什么 |
|---|---|---|---|
| T1 Docker | 手动创建环境和启动 FastAPI | Dockerfile + Compose | 新机器启动时间、命令数、容器内测试通过数 |
| T2 PostgreSQL | 人物、计划和服务保存在进程内存 | SQLAlchemy + Alembic + Repository | 重启恢复率、事务回滚、并发确认唯一性 |
| T3 LangGraph | Python 同进程顺序编排 | StateGraph + PostgreSQL checkpoint | legacy/graph 等价率、节点轨迹完整率、checkpoint 恢复率 |
| T4 Redis | 单实例 Python 锁和内存冷却 | 分布式锁、TTL、短期缓存 | 多实例冲突率、缓存前后 P95、Redis 断开降级成功率 |
| T5 Kafka | 进程内活动记录 | Transactional Outbox + Kafka Consumer | 停机事件补发率、事件丢失数、重复投影数、积压恢复时间 |
| T6 集成 | 各模块分别验证 | Compose + CI + 故障注入 | 一键启动成功率、全链路通过率、故障恢复时间 |

技术只有在产生真实工作路径和测量结果后，才能从“技术栈”变成“项目成果”。

## 9. 面试时怎样解释数字

面试官问“96%怎么来的”时，应按以下顺序回答：

1. **问题**：自然语言计划有随机性，可能方向错误或输出非法。
2. **基线**：冻结模型、提示词和评测集，运行多少条、多少轮。
3. **技术**：修改了提示词契约、快速路径、结构校验或有限重试中的哪一项。
4. **结果**：通过率、降级率、P50/P95分别怎样变化。
5. **边界**：数据是设计的家庭场景，不代表真实用户准确率。
6. **证据**：指出评测集、脚本、原始结果和对应提交。

如果不能完整回答这六项，就不要在简历里写百分比。
