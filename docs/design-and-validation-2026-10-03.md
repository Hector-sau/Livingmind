## 2. 为什么“JSON 合法”还不够

**A valid plan can still mean the wrong thing.**

以前会遇到两种问题：用户说“不要关灯”，关键词解析仍可能看到“关灯”；模型虽然返回合法 JSON，却把“空调凉一点”写成了更高的温度。白名单和数值范围检查挡不住这类错误。

本轮选了两道小范围保护，而不是再加一个付费模型去审核每条请求：

1. **规划前检查限制和冲突。** 对明确识别的否定、只调某设备、保持不变、同一设备相反操作，先请求澄清，不创建计划。用户补充“灯调到 20%”后，用这条新指令重新路由，不能把旧的“不要关灯”拼进去再解析。
2. **模型后检查方向。** 灯光更亮/更暗、空调更凉/更暖、窗帘打开/关闭等已支持表达，要与结构化目标一致。不一致时要求澄清；不会把相反方向的方案交给用户确认。明确的空调方向还会阻止能源建议再次覆盖该目标。

比较基准默认是人物偏好；明确说“比现在/当前/刚才”时，才比较当前设备状态。数值已经达到上下限时允许不变。旧的直接休息接口也不能绕过检查，会返回 `409 CLARIFICATION_REQUIRED`。

**代价：**“只调空调，其他不要动”现在需要用户再给一个明确设备目标，而不是自动生成整晚方案。这是有意收窄范围，保证整晚步骤不会违反限制；不是宣称已经实现复杂约束规划。规则只覆盖代码列出的中文模式，隐喻、跨句指代、双重否定仍可能超出能力。

阅读入口：

- `backend/app/agents/experience/semantics.py`：支持哪些模式、怎样判断方向。
- `backend/app/services/planner.py`：模型结果检查和降级。
- `backend/app/services/rest_service.py`：澄清后的新请求怎样处理。
- `backend/tests/test_semantic_safety.py`：12 条开发回归；本轮先运行得到失败，再修复到通过。
- `apps/mobile/services/mock/agents.ts`、`mockApi.ts`：离线模拟采用相同路由边界。

### 数据集为什么分开

旧 v2 的 h26 已用于定位这轮问题，因此 v2 现在只能作为历史验收与回归材料。旧 JSON 和 29/30 的历史结果未改写，不再把改完后的 v2 叫“没见过的新测试”。开发回归集 r14/r15/r16 的“保留某设备”请求改为澄清，是安全策略改变，不是凭空增加路由准确率。

## 3. 怎样测提速，为什么这次没有默认采用

**Measure the whole API planning request, not just one model call.**

本轮计时从 HTTP 请求发出到计划返回，包含路由、偏好读取、模型、校验和序列化；不含用户确认、设备动作或平板到 Mac 的真实网络。使用隔离内存存储，不读写演示数据库，也不执行设备动作。

假设是：每次请求都重新建立模型连接有开销，复用连接可能降低延迟。两种方式使用同一个模型、提示词、温度 0.3、输出预算 2000 和 HTTP 客户端超时配置 6 秒，交替顺序运行。6 秒是 httpx 的超时配置，不是经过证明的整条链路硬截止时间。

### 本地模型桩：定位连接开销

`backend/scripts/http_plan_bench.py` 测 1 和 5 并发，每种配置两轮、每轮 20 次，合计 160 次有效测量；另有 16 次预热，不计入统计。两组入口 HTTP 客户端设置相同，只切换后端到模型桩的连接复用。

| 并发 | 每次新建连接 P95（两轮） | 复用连接 P95（两轮） |
|---|---|---|
| 1 | 4.881 / 5.069 ms | 1.878 / 1.671 ms |
| 5 | 13.634 / 14.253 ms | 10.386 / 9.443 ms |

原始记录：[http-pooling-2026-10-03.json](evidence/http-pooling-2026-10-03.json)。这是无 TLS、无模型推理的回环实验，只说明连接建立与本机调度开销；不能宣传成 App 提速百分比。

### 真实 DeepSeek：验证用户等待是否改善

用户授权后，使用当前本地配置的 **deepseek-flash**，10 条固定模拟请求、4 个人设、两种连接方式、每种重复两遍，共 40 次真实调用。每组 20 次，全部返回 Token 用量，均通过预置方向检查，无降级。不是比较 chat 和 flash，也不是人工评判完整语义。

| 连接方式 | P50 | P95 | 方向检查通过 |
|---|---|---|---|
| 每次新建 | 1529.759 ms | 2642.971 ms | 20/20 |
| 连接复用 | 1393.337 ms | 2972.948 ms | 20/20 |

中位数约低 8.9%，但 P95 约高 12.5%。小样本、网络波动和模型生成差异都可能影响读数，不能据此声称连接复用普遍更快或更慢。**决策：默认 `LIVINGMIND_MODEL_REUSE_CONNECTIONS=0`，保留开关和测试工具，等更多证据再决定。**没有缓存回复或人物偏好，也没有 Redis 缓存提速结果。

原始记录：[real-http-pooling-2026-10-03.json](evidence/real-http-pooling-2026-10-03.json)。它与历史 96 次模型选型、24 次配对评测的目的和计时范围不同，不合并计算准确率或提速。

第一次测量工具配置错误，FastAPI 在处理带服务对象默认参数的依赖时尝试复制线程锁，40 个 HTTP 请求均在模型前失败，实际模型调用 0 次。已改为无参数闭包并补测试。失败记录单独保存为 `real-http-pooling-setup-failed-2026-10-03.json`，明确排除性能和质量统计；不悄悄删除实验失败。

## 4. 设备可能已执行，回复却丢了，怎么办

**Query the receipt; do not repeat the command.**

之前的保护是记为 `unknown`，重复确认不重发。本轮补充：`POST /api/actions/{action_id}/reconcile`，请求体为 `{"context":{"accountId":"demo-account","personId":"person-lin","spaceId":"space-home-bedroom"}}`。它核对当前人物/空间与动作所属计划，再查询网关回执。

| 查询结果 | 处理 |
|---|---|
| actionId 对应、完成回执有时间和回读值、值符合目标 | 账本与计划中该动作改为完成 |
| 完成回执的值不符合目标，或网关明确失败/拒绝 | 保留为失败/拒绝，不误报成功 |
| 无回执、另一动作的回执、仍受理中、查询超时、时间缺失或早于本次请求 | 继续未知，不再次写设备 |
| 已经有终态 | 不被后来的矛盾回执覆盖 |
| 用户已经停止服务 | 允许补齐旧动作结果，但不恢复服务、不启动余下步骤 |

为什么不能只看“灯现在是 20%”？因为它可能是别人后来调整的，不能证明原来那条动作成功。必须有与 actionId 关联的回执。SQL 实现通过行锁比较当前状态，在同一事务里更新动作账本与计划结果；内存实现使用服务锁。执行器也检查提交/查询回执的 actionId，拒绝把别的动作结果算成成功。

代码入口：`harness/reconciliation.py`、`RestService.reconcile_action`、两种 Store 的 `resolve_unknown_action`；14 条测试在 `tests/test_action_reconciliation.py`，包括丢回执、重复核对、错误 ID、缺失/过期时间、停止后迟到回执、负面终态和人物隔离。

**后续补充：**App 已增加“核对结果（不重发）”，独立网关模式会持久化回执，终态变更只写一次活动记录。原单实例模式仍是进程内网关。直接设备面板动作不具有同等完整的用户侧核对入口，当前按钮针对有计划的动作；不会因核对自动重启服务。演示账户检查不是生产认证。

## 6. 第一批确定的后续顺序

以下为当时的执行计划。当前第 2—4 项已有实现，验证与边界见 [独立网关说明](durable-gateway.md)；第 1 项人工审核仍未完成。依赖修补最新情况见 [依赖风险](dependency-risk.md)。

1. **人工审核 v3 候选标签。** 解决歧义和支持范围，记录审核人与冻结版本。完成标准：每条有预期理由；不能为提高分数而在评测后改标签。
2. **实现独立持久化虚拟网关。** 把设备状态、actionId 回执、空间代次放到独立进程的持久层；把所有写入路径纳入同一协议，包括直接控制和撤销。完成标准：网关重启后仍可查询既有回执，同 actionId 不重复写；不能只把进程内对象包一层 HTTP。
3. **再接两个真实 API 实例。** 两实例共享 SQL/Redis 和上述网关；启动恢复要按执行所有权/租约区分，不能一个新实例启动就取消另一个仍在运行的动作。分别验证同计划确认、不同计划竞争、停止与调整、锁过期、Redis 断连、API 崩溃和网关崩溃。
4. **把对账接到页面与活动记录。** 明确未知、已核对成功、失败、仍未知；活动记录只在状态真正变化时写一次。失败服务是否需要用户另建服务，维持显式确认，不自动续跑。
5. **回归后发布。** 三套后端、契约生成、前端、Docker 浏览器；核对新提交的 GitHub headSha，不沿用旧运行。真机、真实 SpaceMind/厂商设备留作独立验收，不用模拟测试顶替。

原始 Compose 的进程内模式仍不能直接扩成两份共享设备。后续实现须明确启用 `compose.gateway.yaml` 和 replicas profile，不能把原单实例模式与共享网关混跑。

### 你亲自验证时，可以先做这三个实验

每次先写下自己的预测，再读测试和运行结果。答案不需要背术语，重点是能解释“为什么”。

1. **“不要关灯”，再说“灯调到 20%”。** 预测：什么时候产生计划？会不会启动整晚服务？对应 `test_semantic_safety.py` 与前端 `agents.test.ts`。
2. **设备已经写入，但提交回复丢失。** 预测：重复确认会写几次？回执缺失时能否只凭设备数值判成功？用户停止后能否核对旧动作？对应 `test_action_reconciliation.py`。
3. **连接复用本地快，真实模型 P95 却更慢。** 预测：能否宣传提速？如何区分连接、网络、模型与返回解析的耗时？先看两份原始 JSON，再读本页第 3 节。

个人笔记可按“我原来预测 → 实际结果 → 读到哪段代码 → 哪个假设错了 → 如何复测”记录。没有亲自运行的实验请写“阅读并理解”，不要写成自己从零实现或亲自调优。
