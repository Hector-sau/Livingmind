# 演示与测试数据设计

所有数据都是**设计出来的模拟数据**，不是用户数据，也不是真实设备读数。它们的作用是：让演示稳定、让测试覆盖关键路径、让“我们怎么验证”这件事讲得清楚。界面与记录中，模拟来源一律标注。

## 1. 人物与空间（`backend/app/demo/seed.py`，前端 Mock 同步）

| 人物 | 画像 | 休息偏好（灯 / 空调 / 窗帘） | 设计意图 | 演示 PIN |
|---|---|---|---|---|
| 林悦 | 设计师，夜里怕亮，偏暖 | 15% / 25°C / 0% | 暗、暖、全遮光：最典型的“休息” | 2468 |
| 陈川 | 工程师，怕热，留窗帘缝 | 30% / 22°C / 10% | 与林悦在三个维度上都不同，同一句话能看出差异 | 1357 |
| 周禾 | 早睡早起，保留自然光，偏暖 | 20% / 26.5°C / 25% | 小数温度、窗帘半开，覆盖“非整数”和“中间值” | 8024 |
| 访客 | 未选择个人账号 | 空间默认 30% / 25°C / 0% | 共享平板或音箱场景：不读取任何个人偏好 | 无 |

- 三位成员的空调偏好都在 19–27°C 之间，给 ±3°C 的调整带留出上下空间。
- 休息偏好的灯光都不超过 60%，与“休息”语义一致。
- 初始设备状态是“傍晚、灯亮、偏暖、窗帘全开”（80% / 26°C / 100%），确认计划后的变化一眼可见。
- PIN 只防误切换，不是认证：后端不返回 PIN，也不根据 PIN 授权后续请求。

## 1b. 空间规则与能源环境（⑧）

| 数据 | 值 | 用途 |
|---|---|---|
| 空间规则 | 休息时灯光 ≤ 60%；访客不读个人偏好；动作先确认（模拟事件自动调整除外） | “我的”页可见；灯光上限由 Space Execution Agent 和偏好编辑强制 |
| 室外温度 | 29°C（固定模拟值） | 判断是否需要制冷、估算负荷 |
| 高峰电价时段 | 本地 18:00–22:59 | 节能建议触发条件；测试与端到端用 `LIVINGMIND_DEMO_LOCAL_HOUR=20` 固定 |
| 负荷估算 | 0.12 kW × (室外 − 设定) + 0.03 kW × 灯光比例；< 0.5 低档，< 0.9 中档，其余高档 | 只显示档位与估算值，标注“规则估算，非实测” |

## 1c. 主 Agent 路由用例

| 输入 | 意图 | 说明 |
|---|---|---|
| 我想休息 / 把灯关了，我要睡了 | 休息请求 | 含休息词时走完整分支 |
| 把空调调到24度 / 关灯 / 打开窗帘 | 设备指令 | 简化分支，确认后执行，不启动休息服务 |
| 空调调到10度 | 设备指令 → 被 Harness 拦截 | 超出 16–30°C |
| 卧室现在几度 | 状态查询 | 只读回答 |
| 今天股市怎么样 | 其他 | 说明服务范围 |

## 2b. 整晚安排（`backend/app/rules/night_rule.py`，前端 Mock 同步）

模拟时钟 22:30 开始。以林悦（偏好 灯光 15% · 空调 25°C · 窗帘 0%）为例：

| 模拟时间 | 阶段 | 动作 | 规则 |
|---|---|---|---|
| 23:00 | 入睡 | 灯光关闭 | — |
| 01:00 | 深夜 | 空调 26°C | 当晚目标 +1°C，不超过偏好 +3°C |
| 06:30 | 唤醒 1/3 | 窗帘 30%、灯光 20% | 窗帘不低于当晚目标 |
| 06:45 | 唤醒 2/3 | 窗帘 60%、灯光 40%、空调 25°C | 空调回到当晚目标 |
| 07:00 | 唤醒 3/3 | 窗帘 100%、灯光 60% | 灯光不超过空间规则 60%；之后服务 `completed` |

测试用例：逐步推进、空推进（“下一步在 01:00”）、一次推进到底（超过 07:00 按 07:00 计）、完成后再推进被拒、停止后剩余 4 步取消、两个推进并发（只执行一次，共 9 次设备写入）、推进中停止（只有已开始的 1 次写入）。

## 3. 事件序列（`backend/tests/test_events.py`、端到端 `*-event`）

以林悦（偏好 25°C）为例，服务启动后空调为 25°C：

| 序号 | 模拟室温 | 预期 | 覆盖的规则 |
|---|---|---|---|
| 1 | 28°C | 调到 24°C | 偏离 ≥2°C 时调 1°C |
| 2 | 28°C（10 秒后） | 忽略：冷却中 | 冷却时间 |
| 3 | 28°C（35 秒后） | 调到 23°C | 冷却结束 |
| 4 | 35°C 连续 | 22°C 后不再下调 | 不超出偏好 −3°C |
| 5 | 25.5°C | 忽略：无需调整 | 接近设定时不动 |
| 6 | 任意（停止后） | 忽略，设备版本不变 | 停止后不再有动作 |

## 4. Experience Agent 评测集（`backend/evals/experience_cases.json`）

15 条设计用例，按人物和意图分布：

| 标签 | 条数 | 检查什么 |
|---|---|---|
| baseline | 4 | “我想休息”应基本保持本人偏好 |
| temperature | 5 | “热 / 冷 / 别太冷”对应空调方向 |
| light | 2 | “暗一点 / 关灯”对应灯光方向 |
| curtain | 3 | “留条缝 / 全关 / 吵”对应窗帘方向 |
| guest | 2 | 访客以空间默认为基线 |
| guard | 1 | “开到最亮”：最终计划必须在偏离上限内（模型自我克制或被拒绝） |
| off-topic | 1 | 与休息无关：保持偏好 |

打分规则（`app/agents/experience/evaluation.py`）：每条用例对三项设置给出期望方向（下调 / 不变 / 上调 / 不计 / 受限），“不变”允许 ±0.5°C、±5%；结果分为通过、方向错误、降级三类。

两种用法：

- **离线（每次测试都跑）**：`tests/test_eval_cases.py` 用一个“理想模型”替身跑全部用例，验证评测集格式、打分逻辑和偏离上限拦截都正确。它检验的是**方法**，不是模型能力。
- **真实模型（可选）**：在有密钥的电脑上运行 `backend/scripts/e2e_real_model.py --eval`，输出通过率与延迟。这是可选项，不是验收前提。

## 5. 模型桩（`apps/mobile/e2e/fake_deepseek.py`）

浏览器端到端用的本地假接口，按用户话里的关键词给出固定行为：含“慢”→ 超时；含“很亮”→ 提出 100% 灯光（触发偏离上限）；其他 → 合法计划。桩的结果不是模型能力的证据。

## 6. 不做的事

- 不用真实用户数据，不记录任何健康或敏感信息。
- 不把桩或替身的结果写成“模型表现”。
- 真实模型的多次延迟统计是可选项；汇报时只引用已记录的一次真实调用（2035 ms），并说明是单次样本。
